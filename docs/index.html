The problem with hardened forks

An assistant that loads capabilities is, to a security team, a program that runs code which arrived from somewhere. The usual answer is to ship a hardened edition with the dangerous parts removed.

Every hardened fork dies the same way. It drifts. It stops receiving upstream security fixes. Eighteen months later the locked-down build is the least secure thing in the estate.

A strain constrains the kernel from outside it

The brainstem in a locked-down deployment is byte-identical to the one everyone else runs. What changes is the sealed policy around it — so a security fix reaches the restricted deployment the same day it reaches everyone else.

The capability check is the one that is different

Most allowlists trust a manifest field. That is an allowlist of promises. RAPP Light reads the agent's syntax tree and compares what the code can actually reach against what it declared:

$ strainctl approve agents/helper_agent.py

  REFUSED: helper_agent.py reaches capabilities it does not declare:
    process-exec: subprocess.run
    network: requests.post

  Approving this would put an undeclared capability into your estate
  under an approval that does not mention it.

An agent cannot quietly gain reach between review and execution without changing its bytes — and changing its bytes fails the identity check.

Credentials — two keys, two owners

The strain governs what an agent may do. Credentials are what it may hold, and that is a different question with a different owner.

It matters more for agents than for ordinary programs. The moment an agent reads a secret, that value is in the model's context — transmitted to a provider, written to a transcript, possibly reproduced later into a file or a pull request. No amount of scoping or rotation prevents it, because the leak happens at the one operation every traditional secret manager treats as safe.

the machine ── RAPP Keyring ──▸ which PROCESS may hold this secret owned by the user, on the device the estate ── the strain ──▸ which AGENT may cause it to be used owned by the administrator, in sealed policy

Keyring cannot see inside the brainstem — every agent there is one caller. The strain can, because it identifies agents by the sha256 of their bytes. And the strain must never hold a value, because a policy manifest is a file that gets copied and committed. The strain holds grants; Keyring holds values.

The credential organ has no action that returns a secret — not a restricted one, not a flag-gated one. It runs your command with the value injected, and masked in the output. This is what the agent receives from a command that deliberately echoes the secret:

{
  "credentials_injected": ["azure/storage-key"],
  "stdout": "deploying with «redacted:azure/storage-key»\n"
}
$ strainctl cred grant deploy_agent.py 'azure/*'
$ strainctl cred deny  'prod/*'          # outranks every grant, everywhere
$ strainctl cred check deploy_agent.py prod/db
  DENY   deploy_agent.py → prod/db
         denied by the strain rule 'prod/*'

An agent edited after approval loses its grants — the identity check doing double duty. Full model in docs/CREDENTIALS.md.

The band that expands

Enterprise adoption is not binary, so the control is not either. Every capability declares a maturity ring; the organisation declares the band it admits.

frontier▸ private-preview▸ public-preview▸ ga ← you start here

Anything above the standing band needs an individual approval carrying a recorded reason — so one team can pilot one frontier capability without moving the whole population onto the frontier ring.

strainctl approve ./agents/log_detective_agent.py \
  --exception "SRE pilot; review 2026-10-01" --by secops@contoso.example

Every exception appears in strainctl report with its approver and date, so “why is this running in production” always has an answer.

Elevation is a credential, not a build

A locked-down strain and a full brainstem are the same brainstem. An administrator holding the strain credential gets the full surface in the same session — and still cannot approve an agent whose code reaches further than it declares.

you    ▸ what's being held back?
RAPP   ▸ 3 capabilities are withheld by policy. log-detective is at
         public-preview and your band is ga; two others are not approved.
         Your administrator can approve them.

For your security reviewer

What this does not stop

A user with local administrative rights can disable the control — they own the machine. Every endpoint DLP product has the same boundary, and the threat model says so in plain language rather than blurring it.

What it does provide is real and worth naming: it eliminates accidental non-compliance, which is the overwhelming majority of real incidents, and makes deliberate non-compliance leave a trace.

Every mitigation claimed in the threat model has a test named for the threat it covers:

python3 -m unittest discover -s tests -v
# no network · no dependencies · no package index needed
  • Threat model — assets, trust boundaries, ten threats with dispositions, and an explicit out-of-scope list
  • Compliance — data flows, what leaves the machine, retention, audit record
  • RAI posture — what the system decides vs what a human decides, and failure direction
  • Rings — what each maturity ring commits to

Why the kernel stays untouched

This is not a convention someone remembered to follow. RAPP's constitution confines the brainstem to “a loader + an LLM loop + a response splitter” (Article I) and rejects any change that loads responsibility into the kernel which an agent could serve (Article XXVI).

RAPP Light adds zero lines to the brainstem, and continuous integration fails the build if a kernel ever appears in this repository.
